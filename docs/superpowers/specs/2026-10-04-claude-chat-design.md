# Sub-project 4 — Claude chat

Date: 2026-10-04. Parent: [architecture](2026-10-02-architecture-design.md) ("Running Claude", "Chat flow", "Claude ↔ UI contract", "Required follow-ups from the skeleton review"). Builds on [3a](2026-10-03-sync-and-shell-design.md) (shell, mirror) and [3b](2026-10-03-back-channel-design.md) (Claude's edits reach the folder under the hash-guard; per-project settings in SQLite).

## Goal

In the browser the user types in the chat input; Claude Code runs on the home server in the repo's mirror with the user's own setup (subscription login, plugins, MCP, `CLAUDE.md` in `~/.claude`), its answer streams into a **Chat** tab as markdown with rendered mermaid diagrams, tool calls show as compact rows, and commands ask for approval in the chat (by default). Edits Claude makes arrive in the folder through the 3b back channel. Sessions persist: a reload or another device shows the same conversation and can continue it.

## Decisions

| Topic | Decision | Why |
|---|---|---|
| Runner | One `claude` process per turn: `claude -p --output-format stream-json --verbose --include-partial-messages [--resume <claudeSessionId>] --permission-mode <m> [--permission-prompt-tool mcp__aicp__approve --mcp-config <json>] [--model <m>] [--allowedTools <rules…>] --append-system-prompt <convention>`, working directory `<mirror>\<repo>`, the prompt written to stdin (no quoting issues, no length limit), `Agent:Args` appended, `Agent:Env` merged into the environment. Process in a kill-on-close Job object (like `cloudflared`); `Agent:Command` (default `claude`, resolved on `PATH` as `claude.exe`, then `claude.cmd`). Behind the Application port `IAgentRunner` (Infrastructure `ClaudeRunner`). | Architecture decision; subscription login works because the service runs under the user's account; stdin avoids Windows argument quoting. |
| Stream parser | Pure `StreamJsonParser` (Application): one JSON object per line → chat events. `system/init` → the Claude session id; `stream_event` text deltas → `text`; `assistant` content blocks → `message` (authoritative text, replaces the deltas) and `tool` (id, name, input summary); `user` `tool_result` → `toolResult` (id, error flag, first 2 KB); `result` → `result` (ok/error, `total_cost_usd`, `duration_ms`, turns). Unknown types are ignored; a malformed line is logged and skipped. Tested on recorded fixtures. | The CLI's stream format may grow; the parser must not break on additions. |
| Chat events (wire) | Push `chat.event {sessionId, runId, seq, kind, …}`; kinds `text {text}`, `message {text}`, `tool {toolId, name, summary}`, `toolResult {toolId, isError, summary}`, `permission {requestId, tool, summary}`, `permissionResolved {requestId, decision}`, `result {ok, costUsd?, durationMs?, error?}`, `prompt {text}` (the user's message, stored first in its run). Every event ≤ 24 000 bytes serialized (long text is split into several `text`/`message` events, summaries truncated with "…"). `seq` increases per session. | Fits SignalR's 32 KB limit; `seq` lets a client catch up after a reconnect. |
| Sessions and history | SQLite (the 3b `aicp.db`): `chat_session(id, repo, title, claude_session_id, created, updated)`, `chat_event(session_id, seq, json, PK(session_id, seq))`; `text` deltas are not stored (the following `message` is). Title = the first 60 characters of the first message. Messages: `chat.open {repo}` → `chat.sessions {repo, sessions[{id, title, updated, running}]}` and the connection subscribes to the repo's chat; `chat.history {sessionId, afterSeq}` → `chat.events {sessionId, events[], final}` (pages ≤ 24 000 bytes). | Reload, a second tab and the future mobile app all see the same conversation. |
| Send / cancel | `chat.send {repo, sessionId?, text}` (no `sessionId` = new session; text ≤ 16 000 characters) → reply `chat.started {sessionId, runId}` at once; the run continues off the hub invocation (a background task bound to application shutdown), its events are stored and pushed to every connection subscribed to the repo. One run per repo at a time: a second `chat.send` → `error {code: "busy"}` (new code). `chat.cancel {runId}` kills the process tree; the run ends with `result {ok: false, error: "Cancelled."}`. A run survives the browser disconnecting. A run with no output for 10 minutes is killed (`Agent:IdleTimeout`). | Long runs must not block ping/cancel (architecture follow-up); one writer per mirror avoids two agents editing the same files. |
| Permissions | Per-project setting `agentPermissions`: `ask` (default) — `--permission-mode acceptEdits` plus the approval tool, so file edits go ahead and everything else (commands, web) asks in the chat; `all` — `--permission-mode bypassPermissions`, no questions; `settings` — `--permission-mode dontAsk` without the approval tool: only what the user's Claude Code settings allow, the rest is denied. (Flags checked against Claude Code 2.1.288: modes `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan`; `--permission-prompts host` routes prompts to `--permission-prompt-tool`.) **Allow always** adds a rule to the project setting `agentAllowedTools` (`Bash(<command>)` for a shell command, the tool name otherwise), passed as `--allowedTools` from the next turn and answered at once in the current one. | The user's choice (all three as a setting, `ask` by default); edits are safe because the back channel guards the folder. |
| Approval tool | The Server hosts an MCP endpoint (Streamable HTTP, `ModelContextProtocol.AspNetCore`) at `/mcp/approve`, reachable only from loopback with a per-run bearer token (the Access middleware skips exactly this path for loopback; anything else → 404). Its one tool `approve {tool_name, input}` creates a request, pushes `chat.event permission`, waits for `chat.approve {runId, requestId, decision: allow | allowAlways | deny}` and returns `{"behavior":"allow","updatedInput":input}` or `{"behavior":"deny","message":"Denied in the chat."}`. No answer within 10 minutes, a cancel or a server shutdown → deny. `--mcp-config` is passed as inline JSON with the URL and the token header. | Claude Code's documented headless approval hook; loopback + per-run token keeps it unusable from outside. |
| Claude ↔ UI convention | `--append-system-prompt`: "You are used through a web UI. Draw diagrams as ```mermaid fenced blocks. Refer to code as `path:line` relative to the repository root." | Architecture decision; lets the UI render diagrams and link code. |
| Rendering | Markdown → HTML in C# with Markdig (raw HTML disabled, links limited to `http(s)` and `path:line`), shown as `MarkupString`. Mermaid in the browser: `mermaid.min.js` vendored under `wwwroot/lib/mermaid/` (MIT, licence and version recorded in THIRD-PARTY-NOTICES), called from `Scripts/diagrams.ts` with `securityLevel: 'strict'`; a block that fails to render shows its source with the error. `path:line` links open the file's tab (the code viewer comes with the code navigator). | JS only where C# can't (mermaid); no Node: the minified file is committed. |
| UI | The chat input is enabled while connected and a folder is open; **Enter** sends, **Shift+Enter** new line; while a run is going the send button becomes **Stop**. A **Chat** tab per session (title, newest message at the bottom, auto-scroll unless the user scrolled up); a sessions menu in the tab strip (**New chat**, the repo's sessions by last update). Tool calls are collapsed rows (icon, tool, summary; expand for the result). A permission request is a card with **Allow**, **Allow always in this project**, **Deny**. Right status ("status 2"): Claude idle / working… (elapsed), last run's cost. Project settings tab gains: permissions (three radio options with one line each), model (empty = Claude Code's default). | Owner's sketch: centre = tabs incl. chat sessions + chat input; status 2 = agent state. |
| Origin allow-list | A `/hub` request that carries an `Origin` must carry `https://<Server:PublicHost>` (Development also `http://localhost:*`, `http://127.0.0.1:*`), else 403; a request without `Origin` passes (Access is still required): browsers always send `Origin` on WebSocket handshakes and cross-origin requests, which is where cross-site hijacking happens, while same-origin long-polling GETs and native clients (the mobile app) send none. | Architecture follow-up "before Claude chat": the agent makes cross-site WebSocket hijacking an RCE. |
| Token expiry | The Access middleware stores the token's `exp`; the hub aborts a connection when it passes (the client reconnects through Access and gets a fresh token, or the user signs in again). | Architecture follow-up "before Claude chat". |
| Missing `claude` | A run that cannot start (not found, not logged in) ends with `result {ok: false, error}` whose text says what to do ("`claude` was not found on PATH for the service account; set Agent:Command" / Claude's own login message). | First-run clarity. |

## Testing

xunit (CI): `StreamJsonParser` on recorded fixture files (a text answer, tool use with results, an error result, partial messages, unknown and malformed lines); event splitting/truncation (≤ 24 000 bytes); chat store (sessions, events, paging); run orchestration with a fake `IAgentRunner` (one run per repo → `busy`, cancel, idle timeout, events pushed to subscribers and stored, run survives a disconnect); permission broker (allow / allow always → setting + `--allowedTools` next turn / deny / timeout → deny / cancel → deny); `ClaudeRunner` argument building per permission mode and settings (pure); approval MCP endpoint over `WebApplicationFactory` (loopback + token required; tool round trip); Origin allow-list and token-expiry abort on the hub; Markdig rendering (no raw HTML, link filtering, `path:line` links). A real `claude` is never run in tests (the runner process code is a thin `[ExcludeFromCodeCoverage]` class; a fake CLI script is used for one process-level test).
E2E (local, Playwright): send a message with a fake agent command configured (`Agent:Command` → a test script printing fixture stream-json) → streamed answer, a mermaid diagram rendered as SVG, a tool row, a permission card answered **Allow**, Stop.
Manual checklist (`docs/chat.md`): first message on the real home server with the subscription login; a diagram; a command asking for approval in each mode; **Allow always**; Stop; reload during a run; Claude edits a file → it arrives in the folder.

## Known limitations

No image/file attachments in messages; no slash commands or interactive TUI features; one run per repo at a time; costs come from Claude Code's own report (subscription runs report the API-equivalent cost).

## Done when

- A message sent in the browser streams Claude's answer from the home server, with diagrams and tool rows; a command asks for approval in the default mode.
- Sessions survive a reload and continue with `--resume`; Stop works; the Origin and token-expiry follow-ups are in.
- CI green; gate ≥ 85%.

## Out of scope

Code viewer/Monaco and symbol highlighting (code navigator); mobile app; push notifications; other agent CLIs (behind `IAgentRunner` later).
