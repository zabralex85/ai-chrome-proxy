# Chat attachments — paste, drop or pick files and pictures

Date: 2026-10-19. Builds on [4 Claude chat](2026-10-04-claude-chat-design.md) (`ChatService`, `AgentRun`, `ClaudeArguments`, `ChatInput`) and [3 sync](2026-10-03-sync-and-shell-design.md) (chunked upload, base64url). Owner's request: insert pictures and files into the chat from the clipboard or by dragging them.

## What Claude Code offers

- The `Read` tool reads text files, images (PNG, JPEG, GIF, WebP; Claude sees the picture) and PDFs by absolute path.
- `--add-dir <dir>` adds a directory Claude may work in besides the working directory, so reading files there does not ask for permission.
- A resumed session (`--resume`) keeps what `Read` returned in its transcript; the file itself is not needed for later turns.

## Goal

The chat box accepts files: paste (Ctrl+V of a screenshot or copied files), drag and drop from the OS, or the 📎 button. Each shows as a chip above the box (a preview for pictures) and uploads at once; **Send** passes their paths to Claude with the message. Sent messages list their attachments as chips in the history.

## Decisions

| Topic | Decision | Why |
|---|---|---|
| Where files live | `<DataDir>\attachments\<repo>\<id>\<name>` on the server (`Attachments:Root`, default under the data directory, like `Mirror:Root`). Outside the mirror: never synced to the browser folder, never in git. | Owner's choice; attachments are context for Claude, not project files. |
| How Claude gets them | `ChatService.Send` resolves the ids to absolute paths and appends to the text given to Claude (not to the stored `prompt` text): a blank line, `Attached files (read them with the Read tool):` and one `- <absolute path>` per file. `AgentRun` gains `AddDirs`; `ClaudeArguments` adds `--add-dir <attachments\<repo>>` when the message has attachments. | One mechanism for pictures, PDFs and any file; no permission card for reading them. |
| Transport | New hub messages, same shape as `sync.chunk`: `chat.attach` (client → server) `{repo, id, name, size, offset, data, last}`, `data` base64url without padding, at most 16 KB raw; only the last chunk is answered with `chat.attached` `{repo, id}`. `id` is 32 lowercase hex chars generated by the client. Chunks of one upload come in order (offset must equal the bytes stored so far, else `bad_request`). | Reuses the proven chunk scheme; everything stays behind the hub's Origin and Access checks; no new HTTP endpoint. |
| Server storage | `IAttachmentStore` (Application port) with a file-system implementation (Infrastructure). Chunks append to `<id>\<name>.part`; on the last chunk the size must equal `size`, then the file is renamed to `<name>`. Re-sending offset 0 restarts the upload. | Small, testable; mirrors the mirror's temp-then-move. |
| Names | Last path segment only; characters invalid on Windows and control characters → `_`; trailing dots/spaces trimmed; reserved device names (`CON`, `NUL`, ...) prefixed with `_`; at most 100 characters (extension kept); empty → `file`. Every resolved path is checked to stay under the repo's attachments folder. | Untrusted input from the protocol. |
| Limits | 20 MB per file (`too_large` on the chunk that passes it, and when `size` says so up front); at most 10 attachments per message (`chat.send` with more → `too_large`). Per repo at most 50 uploads in progress (`too_large` "Too many uploads in progress."). | Enough for screenshots, logs and PDFs; bounds disk use by one tab. |
| `chat.send` | `ChatSendPayload` gains optional `Attachments` (list of ids, default none). Each must be a finished upload of the same repo, else `not_found` "An attachment has expired; attach it again.". Text may be empty when there is at least one attachment; the text given to Claude is then only the attachment block. | Compatible addition (the Flutter app keeps working). |
| History | `ChatEvent` gains optional `Attachments` (`[{name, size}]`) on the `prompt` event; stored with it in `aicp.db`. The session title of a message without text is the first file name. | Chips in the history after a reload; no file content goes back to the browser. |
| Client: input | `Scripts/chat.ts` listens on the chat box area for `paste` (`clipboardData.files`; text paste is left alone), `dragover`/`dragleave`/`drop` (a highlighted drop zone while dragging files) and the 📎 button's `<input type="file" multiple>`. It keeps each `File` in a map under a handle and tells C# `{handle, name, size, type}`; C# reads bytes with `readAttachmentChunk(handle, offset, length)` and calls `forgetAttachment(handle)` when done. Pasted pictures without a name get `pasted-<yyyyMMdd-HHmmss>.png`. Behind a seam (`IAttachmentSource`) with a thin `[ExcludeFromCodeCoverage]` JS wrapper, like `IFolderAccess`. | Browser APIs only in TypeScript; the upload logic stays in testable C#. |
| Client: chips | Above the textarea: one chip per pending file — preview (object URL, revoked on removal) for `image/*`, else a file icon; name; size; progress while uploading; ✕ removes it (and cancels its upload). A failed upload turns the chip red with the reason. **Send** is disabled while an upload runs or a chip failed; enabled with text or at least one uploaded file. After send the chips clear. In the history the `prompt` bubble lists its attachments as chips (icon by extension, name, size), no preview. | Owner's choice: previews only before sending. |
| Client: upload | `ChatAttachments` (Client/Chat) uploads one file at a time in 16 KB chunks, pipelined like sync, starting as soon as a file is added; it knows nothing about the DOM. Checks 20 MB and 10 files before uploading and says "'name' is larger than 20 MB." / "At most 10 files per message." | Testable with fakes; same limits as the server. |
| Clean-up | At service start, and once a day while it runs, delete attachment folders older than 30 days and `.part` files older than one day. | The transcript keeps what Claude read; old files are only disk use. |
| Not in scope | Dragging a file from the tree (it is already in the repo: write its path); previews in the history; per-repo quotas beyond the in-progress limit; attachments from the Flutter app. | YAGNI. |

## Errors

| Case | Result |
|---|---|
| File over 20 MB, 11th file | Chip not added; note under the box with the reason. |
| Upload fails (connection drop, server error) | Red chip with the reason and ✕; the user removes it and attaches again. |
| Send with an id the server does not know (cleaned up, other repo) | `not_found` "An attachment has expired; attach it again."; text and chips stay in the box. |
| Reconnect during an upload | That upload fails (red chip); no resume. |

## Testing

xunit: name sanitizing (separators, reserved names, length with extension, empty); store (chunks in order, wrong offset, restart at 0, size mismatch, 20 MB, in-progress limit, path stays under root, clean-up by age with a fake clock); `chat.attach` handler (validation, base64url, reply only on last); `ChatService.Send` (attachment block appended to the agent text but not to the stored prompt, `prompt` event carries `{name, size}`, `--add-dir` passed, unknown/foreign id → `not_found`, empty text with attachments accepted, without → `bad_request`, 11 ids → `too_large`); `ClaudeArguments` (`--add-dir` placed so variadic flags are not broken); `ChatAttachments` with a fake source and fake hub (chunking, progress, remove cancels, limits, failure). E2E: paste a picture and drop a file into the chat box, chips show, send → the fake agent's stdin contains both paths and the files exist on the server; the history shows chips after a reload; screenshots dark/light, looked at.

## Done when
